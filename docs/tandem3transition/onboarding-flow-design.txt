1. CURRENT ONBOARDING CAPABILITIES
====================================

The current onboarding is a single static form at:
  apps/dashboard/src/app/onboarding/page.tsx

It collects three fields:
  - Business name (required)
  - First location name (required)
  - Address (optional)

On submit it calls POST /api/locations, then router.replace("/overview").

The experience ends there. No website URL. No AI greeting. No knowledge
extraction. No explanation of what Tandem is or what will happen next.

EXISTING SYSTEMS THAT SUPPORT A RICHER FLOW:

a. Website import pipeline — already fully built:
   - apps/dashboard/src/lib/website-import/run.ts
     runWebsiteImport(url) -> crawlWebsite() -> buildWebsiteImportResult()
   - apps/dashboard/src/lib/website-import/crawl.ts
     Crawls up to a configurable page limit, classifies page types (menu,
     hours, contact, reservations, events, FAQ, memberships, home, about),
     extracts signals (phone, email, address, hours, social links, booking
     platform links).
   - apps/dashboard/src/lib/website-import/extract.ts
     Uses llmGenerate() to produce a structured WebsiteImportDraft from
     crawled page content. Extracts: business name, description, hours,
     FAQs, policies, events, menu sections, reservations, memberships,
     brand colors, logo URL, social links.
   - scripts/worker/website-import-worker.ts
     Async poll-and-process loop. Claims queued onboarding_import_runs rows
     atomically (queued -> running), calls runWebsiteImport, stores result.
   - API routes:
     POST /api/website-import/start   — enqueue a run
     GET  /api/website-import/latest  — poll for status and result
     POST /api/website-import/:id/apply — commit draft to location config

b. WebsiteImportPanel.tsx — review/apply UI already built:
   - Full React component managing: URL input, start, status polling,
     draft preview (FAQs, policies, hours, brand, menu, events), apply.
   - Currently embedded in apps/dashboard/src/app/(console)/knowledge/page.tsx.
   - Includes toggling individual FAQs/policies include/exclude.
   - Reads and writes via the import API routes above.

c. ConsoleSidebar.tsx — a full AI chat panel already in the layout:
   - Present on every console page, left column.
   - Calls /api/operator-chat, streams responses back.
   - Has QUICK_ACTIONS chips ("What should I set up first?",
     "Auto-configure my assistant").
   - Currently read-only — advisory only.

d. Operator chat system prompt (buildOperatorSystemPrompt):
   - Already scoped: "You are Tandem — an AI assistant for restaurant operators."
   - Loads business context from Supabase.
   - Has section for onboarding use case:
     "Setting up chatbot knowledge (menu, hours, policies, FAQs, reservation flows)"

e. knowledge-program.ts — KnowledgeProgram typed model:
   - Fields: hours, menus, reservations, events, memberships, policies,
     FAQs, social links, training controls (tone, shouldAnswer, shouldAvoid).
   - This is the exact target type that import extraction populates.

f. location-config/route.ts — PUT endpoint already handles:
   - assistant_config, knowledge_config, handoff_config, widget_config,
     integrations_config.
   - Supabase auth + membership verification.
   - This is the authoritative write path for all AI-confirmed changes.

g. website-import/apply.ts — merges draft into location config:
   - mergeImportDraftToConfig() deep-merges structured import knowledge
     into business_location_configs.
   - Already handles FAQs, policies, hours, brand theme, structured fields.

SUMMARY: Every building block for a rich AI-guided onboarding flow already
exists as production code. The onboarding page does not use any of them.

2. PROBLEMS WITH CURRENT ONBOARDING
======================================

A. BLANK-SLATE ARRIVAL
After submitting the current three-field form, the operator lands on an
overview page that shows mostly empty state. They must manually navigate to
eight different pages (settings, knowledge, menus, intents, widget, handoff,
locations, account) and fill in dozens of fields. There is no guide, no
AI assistance, and no context for what is needed or why.

B. WEBSITE URL IS NOT COLLECTED
Most restaurants already have a website with hours, menus, contact info, and
FAQs. Tandem has a complete website crawl + extraction pipeline that can
auto-populate 80% of the knowledge base from that URL in under 60 seconds.
The current onboarding never asks for it.

C. NO AI VOICE IN THE FLOW
The operator AI chat sidebar is available on the overview page and all console
pages, but the onboarding flow is a plain HTML form with no conversational
element. There is no greeting. No explanation of what Tandem does. No
warmth. The product's most distinctive feature (AI-first interactions) is
absent from the most important moment in the user journey.

D. VALUE IS DEFERRED, NOT DEMONSTRATED
A restaurant owner signing up for Tandem should experience its core value
(an AI chatbot that knows their restaurant) within the first 5 minutes. The
current onboarding delays this by requiring manual form-filling before
anything is configured. No aha moment is created during onboarding.

E. KNOWLEDGE PAGE IS THE WRONG HOME FOR IMPORT
The WebsiteImportPanel currently lives inside the /knowledge console page.
New operators must: complete basic setup → navigate to knowledge page →
find the import panel → paste URL → wait → review. This is an 8-step process
hidden in a secondary page. For Tandem 3.0, the import should be the first
thing that happens, triggered by the AI during onboarding.

F. NO PROGRESSIVE DISCLOSURE OF WHAT WAS LEARNED
The current apply flow applies the full import draft in one click (or
optionally reviews it in the import panel). There is no moment where the
AI explains to the operator what it found, frames it in human terms, and
asks for confirmation with context. The experience is transactional, not
guided.

G. NO HANDOFF CONTACT COLLECTED DURING ONBOARDING
After configuring knowledge, the most critical piece of information for a
working chatbot is: how do guests reach a human when the bot can't help?
The current onboarding never addresses this. Operators frequently launch
their chatbot with no handoff contact configured.

H. SETUP CHECKLIST IS POST-HOC AND PASSIVE
The current setup checklist on the overview page (import menu, add 3 Q&As,
configure live handoff, install widget) is shown after onboarding ends. It
is a list of things left to do, not an active guide. It never explains why
each item matters and does not use the AI to complete them conversationally.

3. TANDEM 3.0 ONBOARDING PRINCIPLES
======================================

PRINCIPLE 1: THE AI ASSISTANT IS THE GUIDE
Onboarding is a conversation, not a form. The operator reads messages from
the Tandem AI, types replies, and the AI does the work. Forms exist only
where text input of a URL or phone number is required — and those inputs
are embedded inside the chat flow, not on separate pages.

PRINCIPLE 2: CAPTURE THE WEBSITE URL AS STEP ONE
The single most valuable piece of input an operator can give is their
restaurant website URL. Everything downstream (hours, menu, FAQs, contact
info, brand colors) can be extracted from it automatically. The URL must
be collected at the very start of the flow, framed positively: "Your website
is the fastest way to teach Tandem about your restaurant."

PRINCIPLE 3: SHOW WORK IN PROGRESS
During the website scan, the operator should see real-time status updates
that explain what is being discovered. "Looking at your menu... Found your
tasting hours... Reading your contact page..." This is not just polish — it
teaches the operator what Tandem is doing and what kinds of knowledge it
manages.

PRINCIPLE 4: NARRATE THE EXTRACTION
When the scan completes, the AI does not just say "Import complete." It
says: "Here's what I learned about your restaurant." It presents the major
extracted categories — hours, FAQs, contact info, menu summary — in plain
language. The operator should feel like the AI just read their entire website
and summarized it.

PRINCIPLE 5: OPERATOR CONFIRMS, NOT APPROVES LINE BY LINE
The confirmation step should not require reviewing 40 individual FAQ toggles.
The AI presents categories of knowledge ("I found 12 FAQs. Here are the
first three...") and asks for category-level approval. Individual editing
happens later in the chatbot detail view. Onboarding is not the place for
line-by-line review.

PRINCIPLE 6: COLLECT HANDOFF CONTACT BEFORE LAUNCH
After knowledge is confirmed, the AI asks for the primary contact method
(phone number or reservation link). This is framed as: "One more thing —
when guests need to talk to your team, where should the chatbot send them?"
This ensures every chatbot that leaves onboarding has at least one handoff
contact.

PRINCIPLE 7: LAND ON A WORKING CHATBOT
The final step of onboarding shows the operator the new Tandem 3.0 overview
page with their live chatbot preview in the right column. At this moment,
their chatbot already knows their hours, has Q&As populated, and has a
handoff contact configured. The operator's first impression of the dashboard
is: this is working.

PRINCIPLE 8: ONBOARDING IS SKIPPABLE BUT NOT HIDDEN
Operators who want to skip the guided flow should be able to. A "Skip to
dashboard" link is always visible. But the default path should be the guided
AI flow. Operators who skip receive a persistent "Finish setup" prompt chip
in the AI sidebar on the first dashboard visit.

4. AI-GUIDED ONBOARDING FLOW
==============================

The Tandem 3.0 onboarding is a single-page experience at /onboarding.
The page renders the same two-column layout as the console but without
the navigation sidebar. The LEFT panel is the AI chat interface. The RIGHT
panel is a contextual preview that changes with each stage.

STAGE 0: ACCOUNT CREATION (pre-onboarding)
------------------------------------------
Route: /onboarding
Trigger: First time the operator lands post-auth with no business record.

The basic business info is collected first via a minimal form panel on the
right, while the AI greets the operator in the left panel:

LEFT PANEL (AI message):
  "Welcome to Tandem! I'm your restaurant AI assistant.

  I'll help you set up a chatbot that knows your menu, hours, and how to
  handle guest questions — all in the next few minutes.

  First, let's get a few basics so I know your restaurant."

RIGHT PANEL (form):
  ┌─────────────────────────────────────┐
  │  Restaurant name  [____________]   │
  │  First location   [____________]   │
  │  Address (opt.)   [____________]   │
  │                                    │
  │  [ Get started →  ]                │
  └─────────────────────────────────────┘

On submit: POST /api/locations (exact same call as today).
Immediately transition to Stage 1 (no page reload).

Implementation note: The form submission sets a local state flag
  onboardingStage: "website-url"
which replaces the right panel with the Stage 1 panel.


STAGE 1: WEBSITE URL COLLECTION
---------------------------------
Trigger: Business and location records exist. Stage flag = "website-url".

LEFT PANEL (AI message, streamed in):
  "Great, [Restaurant Name] is all set.

  Now — do you have a restaurant website? If you paste the URL, I can

  ┌─────────────────────────────────────────┐

  │  [ Scan my website ] [ Skip for now ]   │
  └─────────────────────────────────────────┘

The URL input is rendered inside the AI message stream as a controlled input

RIGHT PANEL (during Stage 1):
  A simple illustration or placeholder showing:

STAGE 2: WEBSITE SCAN IN PROGRESS
-----------------------------------
Trigger: POST /api/website-import/start returns successfully with runId.

LEFT PANEL (AI message, updated progressively):
  Initial:
    "Scanning [domain.com] now. I'll let you know what I find..."

  As polling updates arrive (via GET /api/website-import/latest
  with runId), the AI message updates in place with the pages being
  visited. This is accomplished by the onboarding state machine subscribing
  to polling events and inserting "status lines" into the AI message:

    "Scanning [domain.com]..."
    "  ✓ Found your homepage"
    "  ✓ Reading your menu..."
    "  ✓ Found your hours page"
    "  ✓ Reading reservations info..."
    "  ✓ Found contact details"
    "  ✓ Checking for FAQs..."
    "  ✓ Extracting knowledge..."

  The status lines are driven by pageClassification results as they are
  populated in the import run record. The polling interval is 2 seconds
  (shorter than the worker's 5-second poll cycle, since the worker may
  have already started processing).

  The page type labels come from the crawl.ts classification:
    "menu" → "Reading your menu"
    "hours" → "Found your hours page"
    "contact" → "Found contact details"
    "reservations" → "Reading reservations info"
    "events" → "Found events page"
    "faq" → "Checking your FAQ page"
    "about" → "Reading about page"
    "policies" → "Found policies page"

RIGHT PANEL (during scan):
  A live progress display shows:
  - Domain URL being scanned
  - "Pages visited: [count] / [limit]"
  - Animated crawl activity (pulsing dots or step tracker)
  - Page type badges appearing as each type is discovered
    (hours, menu, contact, FAQs, reservations — color-coded pills)

  This right panel is the most educational surface in the product.
  It teaches the operator that Tandem understands page types and is
  learning specific topics from each page.

STAGE 2 ERROR HANDLING:
  If the worker returns status "failed":
    If error code "dns_fail":
      AI message: "I couldn't reach [domain.com]. Can you double-check
      the URL? If your site uses a subdomain like 'www.domain.com' or
      a path like '/location', try including that."
      Returns to Stage 1 URL input.
    If error code "blocked":
      AI message: "Your website blocked my scan — this is common with
      some platforms. No worries, I can set things up manually. What are
      your hours?"
      Transitions to Stage 4 (manual setup).
    If error code "timeout":
      AI message: "The scan is taking longer than expected. I've queued
      it in the background. You can continue setting up manually, and I'll
      apply any found data once the scan finishes."
      Transitions to Stage 4 with background scan pending.
    Default:
      AI message: "The scan ran into a problem. Want to try again, or
      should we set things up manually?"
      Offers retry or skip.

5. WEBSITE SCAN WORKFLOW
==========================

SCAN TRIGGER AND ENTRY POINT
------------------------------
The scan is initiated from Stage 1 of the onboarding flow. The operator
types or pastes their URL into the EmbeddedUrlInput component. On clicking
"Scan my website", the onboarding client POSTs to:

  POST /api/website-import/start
  Body: { businessId, locationId, url, source: "onboarding" }

The source: "onboarding" flag allows the backend to:
  a. Track which import runs originated from onboarding (for analytics).
  b. Potentially adjust post-apply behavior (e.g., skip apply confirmation
     and go directly to Stage 3 narration in the onboarding context, rather
     than staying on the knowledge page).

SCAN EXECUTION
---------------
The actual crawl and extraction happen asynchronously in the worker:
  scripts/worker/website-import-worker.ts

The worker:
  1. Polls onboarding_import_runs every 5 seconds for status = "queued".
  2. Claims the row atomically (queued → running) with worker_id.
  3. Calls runWebsiteImport(url) from apps/dashboard/src/lib/website-import/run.ts.
  4. runWebsiteImport() calls crawlWebsite() → buildWebsiteImportResult().
  5. Stores the WebsiteImportResult as result_json in the run record.
  6. Updates status to "succeeded" or "failed" with error code and message.

SCAN PROGRESS POLLING
----------------------
The onboarding UI polls GET /api/website-import/latest?runId=X every 2
seconds to check for status changes and partial results.

The progress display in Stage 2 is driven by:
  - run.status: "queued" | "running" | "succeeded" | "failed"
  - run.result_json.draft.pageClassification (array of { url, pageType })
    Each entry represents a page that was classified.
  - run.result_json.draft.restaurantKnowledge (populated when extraction done)

As pageClassification entries arrive, the left panel AI message adds status
lines for each page type encountered. The right panel updates its discovery
badges in real time.

SCAN LIMITS AND BEHAVIOR
--------------------------
The crawl is governed by WEBSITE_IMPORT_LIMITS in website-import/utils.ts:
  - Maximum pages to crawl (configurable)
  - Request timeout per page
  - Depth limit

The onboarding experience does not need to change these limits. The existing
worker infrastructure handles timeouts and error classification already via
classifyImportError() in the worker.

RESULT DATA STRUCTURE
----------------------
On success, the import run record contains a WebsiteImportResult in result_json:
  {
    draft: WebsiteImportDraft {
      businessName, shortDescription,
      phone, email, address,
      hours (narrative string),
      brand { primaryColor, accentColor, backgroundColor, textColor, fontFamily, logoUrl },
      faqs: ImportFaq[],
      policies: ImportPolicy[],
      restaurantKnowledge: {
        menuSections: ImportMenuSection[],
        events: ImportEvent[],
        reservations: ImportReservationInfo,
        memberships: ImportMembershipInfo
      },
      pageClassification: Array<{ url, title, pageType }>
    },
    sourceUrl, crawledAt, pageCount
  }

This draft is what the Stage 3 narration reads to construct its summary.

6. KNOWLEDGE EXTRACTION PIPELINE
===================================

PIPELINE OVERVIEW
------------------
Website knowledge flows through three sequential stages before being committed
to the chatbot's knowledge base:

  Stage A: CRAWL (crawl.ts)
  Stage B: EXTRACT (extract.ts, via llmGenerate)
  Stage C: APPLY (apply.ts, via location-config PUT)

STAGE A: CRAWL
--------------
crawlWebsite(url) fetches the root page, parses links, scores and prioritizes
candidate URLs using linkPriorityScore(), and crawls up to the page limit.

Classification signals drive the page score:
  - Links in <nav>, <header>, <footer> get higher weight.
  - Paths matching /menu, /hours, /contact, /faq, /reservations, /events get
    HIGH_SIGNAL_PATHS boost.
  - Links to booking platforms (OpenTable, Resy, Tock, Toast, SevenRooms)
    are captured as booking signals.

For each page, extraction produces:
  - textExcerpt (plain text of the page content, truncated)
  - title
  - pageType (classified by path + title pattern matching)
  - The raw HTML is not stored — only the text excerpt and signals.

Signal extraction per page:
  - EMAIL_PATTERN: \b[A-Z0-9._%+-]+@[A-Z0-9.-]+\.[A-Z]{2,}\b
  - PHONE_PATTERN: E.164-like patterns
  - HOURS_PATTERN: Day-of-week followed by time range patterns
  - ADDRESS_PATTERN: US street address pattern
  - BOOKING_PLATFORM_REGEX: opentable, resy, tock, toasttab, sevenrooms

crawlWebsite() returns: { pages: CrawledPage[], signals: ImportSignals }

STAGE B: EXTRACT
-----------------
buildWebsiteImportResult(sourceUrl, pages, signals) calls llmGenerate()
with all crawled page excerpts and a structured extraction prompt.

The LLM produces a RawDraft JSON object which is then normalized into
WebsiteImportDraft. Key extractions:

  HOURS:
    - Narrative: free-text hours string for chatbot knowledge
    - Source URL tracked for attribution
    - Merged with HOURS_PATTERN signal match as fallback

  FAQs (ImportFaq[]):
    - Generated from: explicit FAQ pages (isLikelyFaqPage heuristic),
      policy pages, menu items that could trigger questions,
      reservation info that implies common questions
    - Each entry: { id, question, answer, source_url, include: true }
    - include defaults to true; operator can toggle off in review
    - LLM is prompted to generate FAQ pairs that match real guest queries

  POLICIES (ImportPolicy[]):
    - Extracted from reservation policies, cancellation terms, dining rules,
      dress code, parking, group booking terms
    - Each entry: { id, title, summary, source_url, include: true }

  MENU (ImportMenuSection[]):
    - Section name, items list, dietary flags
    - Stored in restaurantKnowledge.menuSections
    - Surfaced in Stage 3 narration as section count / item count

  EVENTS (ImportEvent[]):
    - Name, description, schedule hints
    - Stored in restaurantKnowledge.events

  RESERVATIONS (ImportReservationInfo):
    - Platform (OpenTable, Resy, etc.), booking URL, guidance text
    - Stored in restaurantKnowledge.reservations

  BRAND:
    - Primary color, accent color, background color, text color (hex)
    - Logo URL (if found in og:image or site header)
    - Font family (if specified in meta/CSS)
    - These feed into the widget theme at apply time

WHAT GETS AUTO-APPLIED TO CHATBOT KNOWLEDGE AT APPLY TIME:
  apply.ts / mergeImportDraftToConfig():
    - hours → knowledge_config.knowledgeProgram.fields.hours
    - faqs (include=true) → knowledge_config.knowledgeProgram.faqs (appended)
    - policies (include=true) → knowledge_config.knowledgeProgram.policies (appended)
    - brand → widget_config.theme (merged via normalizeWidgetTheme)
    - restaurantKnowledge → knowledge_config.knowledgeProgram fields:
        menuSections, events, reservations, memberships
    - businessName, phone, email, address, hours →
        knowledge_config.businessProfile (merged)

WHAT IS NOT AUTO-APPLIED:
  - Social links (informational only, not chatbot knowledge)
  - Source URLs (attribution metadata, not surfaced to guests)
  - Raw HTML (not stored)

FAQ QUALITY HEURISTICS (faq-heuristics.ts):
  isLikelyFaqPage() detects explicit FAQ pages by URL + title patterns.
  normalizeFaqCandidate() cleans up LLM-generated Q&A pairs:
    - Trims whitespace, normalizes question marks
    - Filters out questions that are too short or too generic
    - Deduplicates by semantic similarity (basic string overlap check)

7. CONFIRMATION AND REVIEW UX
===============================

CATEGORY-LEVEL CONFIRMATION IN ONBOARDING
-------------------------------------------
The onboarding confirmation UX is deliberately lighter than the full
WebsiteImportPanel review flow. The goal is speed-to-value, not exhaustive
review. The AI presents category-level summaries and asks for one approval
per category group:

  "I found 12 Q&As. Here are the first three:
   • Do you take reservations? → Yes, book at [link]
   • Are you dog-friendly? → We have a dog-friendly patio
   • Do you have a gluten-free menu? → Yes, ask your server

  Should I add all 12 to your chatbot's knowledge?"

   [ ✓ Add all Q&As ] [ Review individually ] [ Skip Q&As ]

This gives the operator three affordances:
  1. Bulk accept (most common path)
  2. Line-by-line review (opens Stage 3b inline review panel)
  3. Skip entirely (the chatbot will still work; Q&As can be added later)

CATEGORY GROUPS PRESENTED IN STAGE 3:
  1. Hours — single confirmation ("I found your hours. Does this look right?")
  2. Q&As (faqs) — count + 3 examples + bulk confirm
  3. Contact info — phone / email / booking link preview + confirm
  4. Menu — section count summary (no line-by-line in onboarding)
  5. Brand colors — color swatches, brief confirm ("Using your site's colors")

WHAT IS SKIPPED DURING ONBOARDING REVIEW:
  - Individual policy items (applied by default, editable later)
  - Individual menu items (applied by default, editable later)
  - Events, memberships (applied by default, shown in /chatbot > Knowledge later)
  - Brand font (applied by default)

INLINE REVIEW PANEL (Stage 3b):
  When operator clicks "Review individually" for Q&As, the right panel
  switches to a simplified WebsiteImportPanel showing only the FAQs section.
  Each FAQ has an include/exclude toggle. The "Apply" button re-calls
  POST /api/website-import/:runId/apply with updated include flags.

  This is the same WebsiteImportPanel.tsx component already built. In the
  onboarding context it is stripped of the URL input, status polling, and
  the "Apply all" bulk section — only the FAQ list with toggles is shown.

CONFLICT RESOLUTION:
  If the operator already manually entered hours in Stage 4 (manual path)
  and then the background scan completes with different hours, the AI
  prompts: "The website scan found different hours from what you told me.
  Which is correct: [website hours] or [what you said]?"
  The operator picks one, and the selected value is saved via PUT /api/location-config.

CHANGE PERSISTENCE:
  All confirmed changes are written to business_location_configs in Supabase
  via the apply endpoint or PUT /api/location-config. MockState in localStorage
  is updated in parallel using updateMockState() so that the overview page
  panels reflect the changes immediately without requiring a Supabase read
  on every navigation.

POST-ONBOARDING REVIEW ACCESS:
  After onboarding completes, the operator can return to any extracted item
  via the /chatbot page (Tandem 3.0 nav). The /chatbot > Knowledge tab shows
  all FAQs with edit/delete. The /chatbot > Behavior tab shows tone and
  training rules. Individual items can be edited by talking to the AI sidebar
  on any page.

ROUTING LOGIC (when to show onboarding):
-----------------------------------------
  The current route guard at apps/dashboard/src/middleware.ts (or equivalent)
  should redirect to /onboarding when:
    - User is authenticated
    - User has no business membership record
  
  And also conditionally when:
    - User has a business but onboarding_completed flag is false
      (add onboarding_completed boolean to businesses or business_memberships table)
  
  After onboarding completion: set onboarding_completed = true on the business
  membership record. This prevents re-showing onboarding on subsequent logins.
  The DB migration for this field is minimal (one boolean column with default false).


API ROUTE CHANGES SUMMARY:
---------------------------
  No new API routes required for Phase 1 — all existing routes are reused.

  Optional additions for Phase 2+:
    GET /api/onboarding/status
      Returns: { stage, hasWebsiteUrl, lastImportRunId, onboardingComplete }
      This allows the UI to resume onboarding state on page refresh.

    POST /api/onboarding/complete
      Marks onboarding_completed = true on the business membership.
      Called when operator clicks "Go to my dashboard" in Stage 6.

  These are one-line route handlers using existing Supabase client patterns.


DATABASE CHANGES REQUIRED:
----------------------------
  MINIMAL — only one new column needed for Phase 1:
    ALTER TABLE businesses ADD COLUMN onboarding_completed BOOLEAN DEFAULT false;
  
  OR alternatively on business_memberships:
    ALTER TABLE business_memberships ADD COLUMN onboarding_completed BOOLEAN DEFAULT false;
  
  The per-membership version is preferred so that if an employee is added to an
  existing business, their first login doesn't re-trigger onboarding.

  No other schema changes are required for the onboarding flow. The existing
  onboarding_import_runs table already handles all scan state.

  New migration: supabase/migrations/<timestamp>_onboarding_completed.sql
