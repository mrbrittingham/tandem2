HIGH-LEVEL REPO STRUCTURE
--------------------------
This is an npm workspaces monorepo. Root package.json: name="tandem2", version="2.0.0".

Workspaces:
  apps/dashboard        — Next.js 16 App Router, port 3100
  packages/shared       — @tandem/shared: types, mock-store, LLM client, storage, server helpers
  packages/ui-kit       — @tandem/ui-kit: ChatWidget + design system primitives

Async worker (not a workspace):
  scripts/worker/website-import-worker.ts   — polls Supabase, processes queued import jobs

Supabase config:
  supabase/            — authoritative CLI config + migration path
  supabase/migrations/ — active migration path used by `supabase db push`

Other root-level artifacts:
  main.py / pyproject.toml   — Replit NixOS boilerplate. No runtime function.
  replit.md                   — Replit-oriented readme; largely duplicates README.md
  .replit                     — Replit workflow/port config; also embeds live credentials in [userenv.shared]
  docs/                       — Architecture docs, transition plans, chatbot docs
  scripts/                    — Dev, deploy, migration, smoke-test, guard CLI scripts

MAIN RUNNABLE APP
-----------------
`apps/dashboard` is the sole primary runtime. `npm run dev` starts it on port 3100.
Package name inside that directory is "dashboard" (not "tandem-dashboard").
The root `package.json#name` is "tandem2" — a stale artifact from v2.0 naming.
No second app or server exists. The website-import worker (`scripts/worker/`) is
the only approved async exception and is launched separately via `npm run worker:imports`.

WHERE ENV SHOULD CANONICALLY LIVE
-----------------------------------
There is only one correct runtime env file for this repo:

  → apps/dashboard/.env.local

Reasons:
  1. Next.js inherently reads .env.local from the app directory when running
     `next dev`. It does NOT auto-load root-level .env files.
  2. All npm scripts that need env vars explicitly pass
     --env-file=apps/dashboard/.env.local (see package.json lines 18-26).
  3. apps/dashboard/.env.example is the template for this file and is committed.
  4. The RUNBOOK and .env.example at the root both say to put values in this file.

IS ROOT .env JUSTIFIED?
------------------------
No. Root .env contains wrong variable names (SUPABASE_URL vs NEXT_PUBLIC_SUPABASE_URL)
and is never loaded by any script. It is entirely unused and should be deleted.

IS ROOT .env.local JUSTIFIED?
-------------------------------
No. Root .env.local is never loaded by any script in package.json. It duplicates
apps/dashboard/.env.local with a CONFLICTING and INVALID value of LLM_MODEL=gpt-5.2.
It should be deleted to prevent confusion.

IS .env.vercel.import JUSTIFIED?
----------------------------------
Partially. It serves a real purpose: it's a list of env vars to paste into the
Vercel dashboard import UI. However:
  - It contains real credentials (production OPENAI key, Supabase keys) in a format
    that appears template-like but contains live values.
  - LLM_MODEL=gpt-5.2 is invalid and would cause production failures if imported.
  - It should be converted to a true template with placeholder values and a comment
    block explaining that real values must be substituted before use.
  - If the file must contain real values for operational convenience, it should
    at minimum be renamed .env.vercel.import.FILL-ME-IN or documented clearly.

SHOULD .replit REMAIN?
------------------------
Yes, for Replit compatibility. However:
  - [userenv.shared] contains hardcoded production credentials (OPENAI_API_KEY).
    This means they are committed to source control. This is a risk.
  - Replit's recommended approach is to use Replit Secrets (dashboard) not
    hardcoded values in .replit config files.
  - The [userenv.shared] block should have its values replaced with empty strings
    and a comment directing operators to set values via Replit Secrets.
  - The workflow definition (`npm run dev`) and port mapping (3100 → 80) are
    correct and should remain.

RISKY DUPLICATION SUMMARY
---------------------------
1. ROOT .env ←→ apps/dashboard/.env.local:
   Duplicate values, wrong key names in root. Root file is unused.

2. ROOT .env.local ←→ apps/dashboard/.env.local:
   Duplicate values + CONFLICTING LLM_MODEL (gpt-5.2 vs gpt-4o).
   Root file is unused. Risk: developer edits root file assuming it affects runtime.

3. apps/dashboard/.env.local ←→ .replit [userenv.shared]:
   Both supply OPENAI_API_KEY and NEXT_PUBLIC_SUPABASE_* values.
   Key values appear to differ (different API key strings). If Replit is running
   the app, its [userenv.shared] values win over the app .env.local.
   This could cause the app to work locally but use a different key in Replit.

4. apps/dashboard/.env.local ←→ .env.vercel.import:
   Both have OPENAI_API_KEY; different key values (Key-A vs Key-B).
   The .vercel.import has a different and presumably production key — having
   a committed file with a production key is a risk.

NOTE ON DOTENV USAGE:
  No dotenv package is imported or used anywhere in the codebase. All env loading
  is handled by: (a) Node's built-in --env-file flag, (b) Next.js built-in .env.local
  loading, or (c) Replit's [userenv.shared] injection. This is correct.
