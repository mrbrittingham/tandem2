1. HIGH-LEVEL TRANSITION STRATEGY
====================================

TANDEM 2.0 STATE (starting point)
  - 12 form-based console pages managed by operators manually.
  - AI sidebar (ConsoleSidebar.tsx) is advisory only — read-only text responses.
  - Website import pipeline exists but is buried in the Knowledge page.
  - Onboarding is a 3-field form with no AI involvement.
  - Mock state in localStorage is the primary runtime state.
  - No operator chat session persistence.
  - No usage tracking or cost controls.
  - Every configuration action requires human navigation and form submission.

TANDEM 3.0 TARGET STATE
  - AI sidebar is the single write surface — operators type to configure.
  - Dashboard pages are read-only reflections of chatbot state.
  - Onboarding is conversational — AI guides operators through setup in minutes.
  - Website import feeds directly into onboarding, not a secondary page.
  - 4 top-level nav sections replace 9+ CRUD pages.
  - Configuration changes persist to Supabase via authenticated tool execution.
  - UI refreshes instantly after AI-confirmed changes (no page reload).
  - Token usage is tracked internally for cost visibility.

TRANSITION PRINCIPLES
---------------------

1. PRESERVE THE CUSTOMER CHATBOT.
   The customer-facing chat stack (/api/chat, chat-handler.ts, ChatWidget.tsx)
   is production-quality. Every phase must treat it as read-only. No
   refactoring, no route changes, no behavior modifications. The guardrails,
   streaming, injection detection, and KnowledgeProgram-based system prompt
   are correct as built.

2. ADDITIVE-FIRST, DESTRUCTIVE-LAST.
   New pages and routes are created before old ones are deleted. Redirects
   are added before old page files are removed. This ensures no broken
   navigation at any stage during development.

3. BACKEND BEFORE FRONTEND.
   The AI tool calling backend (Phase 3) should be built and validated via
   API testing before the confirmation UI (Phase 4-5) is wired. You can
   verify /api/operator-chat/confirm writes correctly to Supabase with curl
   before ConsoleSidebar is updated.

4. FEATURE FLAGS ARE NOT NEEDED.
   Each phase produces a shippable increment that does not break the existing
   system. Pages being rebuilt receive new routes first; old routes redirect
   after the new destination is complete. The 2.0 pages remain accessible
   until explicitly removed in Phase 4.

5. MOCK STORE IS A BRIDGE, NOT THE DESTINATION.
   In the transition period, the mock store in localStorage remains the
   local state layer. AI-confirmed writes update both the mock store AND
   Supabase. The mock store remains correct for all dashboard rendering.
   Moving to fully server-authoritative UI reads is a post-3.0 concern.

6. SECURITY IS NON-NEGOTIABLE AT EVERY PHASE.
   The AI tool calling surface (Phases 3-5) is a new write path into the
   database. Every change must be: authenticated (Supabase session), authorized
   (membership check), validated (zod schema), logged (console.info with
   userId, locationId, toolName). These checks are not optional and cannot
   be deferred.

7. TYPE SAFETY THROUGHOUT.
   npm run typecheck must pass at the end of each phase. No phase ships with
   TypeScript errors. Lint must also pass. These gates are the primary
   automated quality checks available in this codebase.

3. PHASE 1 — STABILIZE WEBSITE IMPORT PIPELINE
=================================================
Dependency: None (this is the first phase)
Estimated effort: 2–3 days
Owner: 1 engineer

CONTEXT
--------
The website import pipeline is the foundational data-flow that feeds the new
onboarding experience (Phase 2). Phase 2 depends entirely on the pipeline
being reliable, reporting accurate error codes, and providing progress data
that the onboarding UI can poll. The current worker is functional but has
not been hardened for the onboarding use case.

GOAL
-----
The pipeline must be stable enough that:
  a. The onboarding UI can reliably poll import status and display progress.
  b. Error cases are categorized with codes the UI can branch on.
  c. The worker does not silently drop jobs or fail without updating status.
  d. A source:"onboarding" field is accepted so onboarding-triggered runs
     are distinguishable from knowledge-page-triggered runs.

FILES TO MODIFY
----------------
  scripts/worker/website-import-worker.ts
    - Ensure every error path sets status="failed" with an error_code field.
    - Define and handle these error codes:
        "dns_fail"  — URL unreachable (ENOTFOUND, ECONNREFUSED)
        "blocked"   — HTTP 403/429, bot-blocking response
        "timeout"   — crawl or extraction exceeded time limit
        "parse_error" — malformed HTML preventing classification
        "llm_error" — LLM extraction call failed
    - Wrap the entire claim → process → store cycle in try/catch. A worker
      crash must not leave a run stuck in "running" with no error update.
    - Add a stale-job reaper: any run in "running" status for more than 5
      minutes with no update should be reset to "failed" with error_code
      "timeout" on next worker poll cycle.
    - Log each job claimed, completed, and failed with run ID.

  apps/dashboard/src/app/api/website-import/start/route.ts
    - Accept and persist a source field in the request body (valid values:
      "knowledge-page" | "onboarding"). Default to "knowledge-page".
    - Store source in the onboarding_import_runs row.
    - Validate the URL is a well-formed https:// URL before queuing.
      Reject http:// or javascript: scheme URLs with a 400 error.

  apps/dashboard/src/app/api/website-import/latest/route.ts
    - Confirm this route returns partial results: status, pageClassification
      array, and run.result_json when available.
    - If called with runId query param, return data for that specific run.
    - Ensure the response includes error_code when status="failed".

  apps/dashboard/src/lib/website-import/run.ts
    - Verify runWebsiteImport() propagates the structured error codes above.
    - Ensure crawl page limit is configurable and respected (default 20 pages).
    - Do not throw unstructured errors — return a typed result or throw with
      a recognizable error shape.

  apps/dashboard/src/lib/website-import/crawl.ts
    - Confirm pageClassification results are being written incrementally
      to result_json as they are discovered (not only at completion).
      The onboarding Stage 2 progress display depends on incremental updates.
    - If partial writes are not already implemented, add them.

DATABASE MIGRATION
-------------------
  Migration: Add source and error_code columns to onboarding_import_runs.
  File: supabase/migrations/YYYYMMDDHHMMSS_import_runs_source_and_error.sql

  ALTER TABLE onboarding_import_runs
    ADD COLUMN IF NOT EXISTS source TEXT NOT NULL DEFAULT 'knowledge-page',
    ADD COLUMN IF NOT EXISTS error_code TEXT;

  Create via: npm run migration:new -- import_runs_source_and_error

BACKEND CHANGES
----------------
  - POST /api/website-import/start: validate URL scheme, persist source field.
  - GET /api/website-import/latest: include error_code in response when present.
  - Worker stale-job reaper: add 5-minute timeout recovery on poll cycle.

ACCEPTANCE CRITERIA
--------------------
  [ ] Worker claims a queued job and processes it.
  [ ] Worker handles DNS failure (ENOTFOUND) → sets status="failed",
      error_code="dns_fail".
  [ ] Worker handles HTTP 403/429 → sets status="failed", error_code="blocked".
  [ ] Worker handles LLM timeout → sets status="failed", error_code="timeout".
  [ ] A job accidentally left in "running" for 5+ minutes is auto-recovered.
  [ ] GET /api/website-import/latest?runId=X returns pageClassification
      incrementally during run.
  [ ] POST /api/website-import/start rejects javascript: or non-http(s) URLs.
  [ ] source="onboarding" is stored and returned in the run record.
  [ ] npm run typecheck passes.

4. PHASE 2 — BUILD NEW ONBOARDING FLOW
=========================================
Dependency: Phase 1 complete
Estimated effort: 3–5 days
Owner: 1 engineer

CONTEXT
--------
The current onboarding is a 3-field form that drops operators on an empty
overview page with no guidance. The full design specification is in:
  docs/tandem3transition/onboarding-flow-design.txt

The onboarding is a single-page AI-guided experience with 6 stages:
  Stage 0: Business/location creation form (right panel) + AI greeting
  Stage 1: Website URL collection embedded in AI chat
  Stage 2: Live scan progress (polling) with page-type discovery display
  Stage 3: Scan results narration — AI summarizes what it found
  Stage 3b: Optional detailed review using WebsiteImportPanel
  Stage 4: Manual fallback path (scan failed or skipped)
  Stage 5: Handoff contact setup
  Stage 6: Completion — live widget preview + transition to dashboard

NOTE: Stage 4's AI-driven variant (tool calling for set_business_hours,
set_handoff_contact, add_faq) requires Phase 3 to be complete. Stage 4
must be implemented with a form-based fallback for Phase 2, then upgraded
in Phase 5 once tool calling is live.

FILES TO CREATE (new)
----------------------
  apps/dashboard/src/app/onboarding/components/EmbeddedUrlInput.tsx
    A controlled input component rendered inside the AI chat stream.
    Props: onScan(url: string), onSkip().
    Validates URL format client-side before calling onScan.

  apps/dashboard/src/app/onboarding/components/ScanProgressPanel.tsx
    Right-panel component for Stage 2. Displays:
    - Domain URL being scanned.
    - Animated activity indicator.
    - "Pages visited: [count]" counter.
    - Color-coded page type badges (hours/menu/contact/FAQs/reservations)
      appearing as pageClassification entries arrive.

  apps/dashboard/src/app/onboarding/components/ScanResultsSummary.tsx
    Right-panel component for Stage 3. Displays category cards:
    Hours | Menu | Q&As | Contact | Brand.
    Each card shows found/not-found state (emerald/orange).

  apps/dashboard/src/app/onboarding/components/HandoffContactInput.tsx
    Embedded form for Stage 5 with three input fields (phone, link, email)
    and Save / Skip buttons. Calls PUT /api/location-config directly
    in Phase 2 (tool-calling upgrade in Phase 5).

  apps/dashboard/src/app/onboarding/hooks/useImportPolling.ts
    Custom hook that polls GET /api/website-import/latest?runId=X every
    2 seconds. Returns: { status, pageClassification, draft }, stops polling
    when status is "succeeded" or "failed". Exports the error_code when
    status is "failed".

  apps/dashboard/src/app/onboarding/lib/onboarding-state-machine.ts
    Type-safe state machine (or useReducer) managing onboardingStage:
    "business-form" | "website-url" | "scanning" | "scan-results" |
    "scan-review" | "manual-setup" | "handoff" | "complete"
    State transitions are event-driven (form submit, scan start, scan
    complete, apply, skip, etc.). This module has no UI dependencies.

FILES TO MODIFY
----------------
  apps/dashboard/src/app/onboarding/page.tsx
    Full rewrite. The existing 3-field form logic is replaced.
    Structure: two-column layout (left: AI chat thread, right: contextual panel).
    No top navigation is rendered on this page (standalone auth experience).
    The AI chat thread is a controlled list of message bubbles. It is NOT
    wired to /api/operator-chat — messages are programmatic (the onboarding
    state machine drives them). The operator's typed replies drive state
    transitions only in Stage 4 (manual setup).

    Stage routing in the component:
      switch (onboardingStage) {
        case "business-form":    → right panel = <BusinessSetupForm />
        case "website-url":      → left panel message + <EmbeddedUrlInput />
        case "scanning":         → right panel = <ScanProgressPanel />
        case "scan-results":     → right panel = <ScanResultsSummary />
        case "scan-review":      → right panel = <WebsiteImportPanel />
        case "manual-setup":     → left panel = conversational Q&A
        case "handoff":          → left panel message + <HandoffContactInput />
        case "complete":         → right panel = <ChatWidget config={...} />
      }

REUSED EXISTING COMPONENTS
----------------------------
  apps/dashboard/src/components/WebsiteImportPanel.tsx
    Reused as-is for Stage 3b (detailed review). The component must be
    validated to work correctly outside the knowledge page context.
    Pass the runId as a prop; the panel uses POST /api/website-import/:id/apply.

  packages/ui-kit/src/ChatWidget.tsx
    Used in Stage 6 completion (right panel live preview).
    businessToWidgetConfig(activeBusiness) provides the config.

API ROUTES USED (ALL EXISTING — NO NEW ROUTES REQUIRED)
---------------------------------------------------------
  POST /api/locations               Stage 0: create business + location
  POST /api/website-import/start    Stage 1: trigger the scan
  GET  /api/website-import/latest   Stage 2: poll for progress
  POST /api/website-import/:id/apply Stage 3: commit import to config
  PUT  /api/location-config         Stage 5: save handoff contact directly

DATABASE MIGRATIONS
--------------------
  None required in Phase 2 beyond Phase 1's migration.
  (The onboarding_import_runs.source field added in Phase 1 supports
  the source:"onboarding" flag used here.)

FRONTEND CHANGES
-----------------
  - /onboarding: Complete page rewrite. Two-column layout, stage machine,
    6 stages, progressive AI chat narration.
  - Stage 4 (manual path) in Phase 2 uses form inputs in the right panel
    wired directly to PUT /api/location-config. This is the temporary
    form-based fallback. Tool-calling upgrade is Phase 5.
  - "Skip to dashboard" link visible at all times.
  - On skip: call router.replace("/overview"). No state is applied.
    The AI sidebar on /overview shows a "Finish setup" chip for operators
    who skipped.

ACCEPTANCE CRITERIA
--------------------
  [ ] Stage 0 → Stage 1 transition works after form submit.
  [ ] Stage 1 URL input validates format before scan starts.
  [ ] Stage 2 polling updates left panel with page type lines as they arrive.
  [ ] Stage 3 shows narrated summary with correct counts from draft.
  [ ] Stage 3b review panel allows individual FAQ/policy toggles.
  [ ] Apply in Stage 3/3b calls POST /api/website-import/:id/apply.
  [ ] Stage 4 collects hours, contact, 1 FAQ via form fallback.
  [ ] Stage 5 saves handoff contact to PUT /api/location-config.
  [ ] Stage 6 shows live ChatWidget with applied configuration.
  [ ] "Skip to dashboard" is visible and functional at every stage.
  [ ] DNS failure in scan transitions to Stage 4 with error message.
  [ ] Blocked scan transitions to Stage 4 with explanation.
  [ ] npm run typecheck passes.

5. PHASE 3 — IMPLEMENT OPERATOR AI TOOL ARCHITECTURE
======================================================
Dependency: Phase 1 (for confirmed understanding of existing write paths)
Note: Can run in parallel with Phase 2 (no file conflicts)
Estimated effort: 8–12 days
Owner: 1 engineer (dedicated backend focus)

CONTEXT
--------
This is the most complex and highest-risk phase. The full design specification
is in: docs/tandem3transition/operator-ai-tool-architecture.txt

Phase 3 adds tool/function calling to the operator AI so it can propose and
execute configuration changes (hours, FAQs, handoff contacts, behavior rules,
business info). Every change requires an explicit operator confirmation step.
No change is ever applied automatically.

Read operator-ai-tool-architecture.txt §1–§9 in full before writing any code.

THE 9 OPERATOR TOOLS
---------------------
  1. set_business_hours     → knowledge_config.knowledgeProgram.fields.hours
                               knowledge_config.businessProfile.hours
  2. add_faq                → knowledge_config.knowledgeProgram.faqs (append)
  3. update_faq             → knowledge_config.knowledgeProgram.faqs (update by id)
  4. remove_faq             → knowledge_config.knowledgeProgram.faqs (filter by id)
  5. set_handoff_contact    → handoff_config.contactMethods (upsert by id)
  6. remove_handoff_contact → handoff_config.contactMethods (filter by id)
  7. update_handoff_settings → handoff_config (top-level field merge)
  8. set_behavior_rules     → knowledge_config.knowledgeProgram.training
  9. update_business_info   → knowledge_config.businessProfile (partial merge)

PHASE 3 SUB-PHASES
-------------------

PHASE 3A: TOOL DEFINITIONS + LLM INTEGRATION (2–3 days)
  3A.1 Install zod if not already in apps/dashboard dependencies.
  3A.2 Create apps/dashboard/src/lib/operator-tools/tool-definitions.ts
       - Export a `tools` array using the Vercel AI SDK `tool` helper.
       - Each tool has: description, parameters (zod schema).
       - Parameter schemas match the JSON Schema spec in operator-ai-tool-
         architecture.txt §2 exactly.
  3A.3 Modify apps/dashboard/src/app/api/operator-chat/route.ts:
       - Import generateText from the ai package (Vercel AI SDK).
       - Import the tools array from tool-definitions.ts.
       - Split the POST handler into two branches:
           Branch A (default): existing streaming path via handleChatPost()
             unchanged. Returns text/plain stream.
           Branch B (when tools should be considered): call generateText with
             tools, toolChoice: "auto". If result.toolCalls.length > 0,
             construct PendingChange and return application/json.
       - The tool-enabled branch triggers for ALL operator messages in this
         phase. The LLM decides via toolChoice:"auto" whether to call a tool.
  3A.4 Test with curl: POST to /api/operator-chat with message
         "Set our hours to Monday-Friday 11am to 10pm, closed weekends"
       Expected response: Content-Type: application/json, body contains
         { pendingChange: { toolName: "set_business_hours", toolArgs: {...},
           humanSummary: "..." }, assistantMessage: "..." }
  Checkpoint: Tool detection and PendingChange construction works via API.

PHASE 3B: CONFIRM ENDPOINT + TOOL EXECUTOR (2–3 days)
  3B.1 Create apps/dashboard/src/lib/operator-tools/tool-executor.ts
       - Export: executeOperatorTool(toolName, toolArgs, locationId,
         businessId, supabase): Promise<{ updatedConfig: ... }>
       - Each tool implementation MUST follow this pattern:
           a. Fetch current config via GET /api/location-config (or via
              Supabase client directly to avoid HTTP round-trip in server context)
           b. Apply the in-memory change (deep merge, array append/filter)
           c. Build the partial payload for PUT /api/location-config
           d. Execute the PUT and return the updated config sections
       - CRITICAL: Never partially write array columns. Always fetch → mutate
         in memory → write the full array. Failing to do this destroys all
         existing FAQs or contacts except the one being written.
       - Validate toolArgs against expected shape before applying. Drop
         unknown fields. Cap string lengths (question/answer: 1000 chars,
         narrative: 500 chars, URLs: no javascript: scheme).
       - sanitizeKnowledgeConfig() must be respected for update_business_info
         — do not write locationName or address fields.
  3B.2 Create apps/dashboard/src/app/api/operator-chat/confirm/route.ts
       - POST handler. Auth: createSupabaseServerClient() + getUser().
         Reject unauthenticated requests with 401.
       - Re-resolve the operator's businessId and locationId from authenticated
         membership (not from the pendingChange payload). Use the same
         resolveLocationId() pattern as in location-config/route.ts.
       - Validate that the pendingChange.locationId matches the re-resolved
         locationId. Reject with 403 if mismatch.
       - Validate toolArgs via zod against the schema for the named tool.
         Reject with 400 if validation fails.
       - Call executeOperatorTool(). On error, return 500 with error message.
       - Return { ok: true, updatedConfig: { ... } } on success.
       - Log each confirmed execution: userId, locationId, toolName, summary
         of changed fields (not full values).
  3B.3 Manual integration test: craft a POST to /api/operator-chat/confirm
       with hardcoded pendingChange matching add_faq. Verify:
         - The FAQ appears in Supabase business_location_configs.knowledge_config.
         - Re-testing with a different authenticated user's locationId fails
           with 403.
         - Testing with invalid toolArgs fails with 400.
  Checkpoint: Confirm endpoint writes correct data, rejects invalid auth/args.

PHASE 3C: UI CONFIRMATION FLOW (2 days)
  3C.1 Create apps/dashboard/src/lib/operator-tools/pending-change-renderer.tsx
       - ConfirmationCard component.
       - Props: pendingChange, assistantMessage, onConfirm(), onCancel().
       - Renders: explanation text, structured human-readable summary of
         the proposed change (formatted per tool type), [Confirm] and
         [Cancel] buttons.
       - Visual style: distinct from normal message bubbles (bordered card,
         light highlight background). Use ui-kit primitives where available.
       - Tool-specific rendering:
           add_faq: shows question + answer in quote block
           set_business_hours: shows day/time table
           set_handoff_contact: shows type icon + label + value
           update_business_info: shows changed fields as key/value list
           All others: show a summary sentence from humanSummary field.
  3C.2 Extend apps/dashboard/src/components/ConsoleSidebar.tsx:
       - Extend the Message type: add type field:
           type Message = { role: ...; text: string; type: "text" |
             "pending_change" | "confirm_success" | "confirm_error" }
         Add pendingChange?: PendingChange to Message.
       - In sendMessage(), after receiving the response:
           If Content-Type is application/json and body.pendingChange exists:
             append an assistant message with type:"pending_change" and
             pendingChange set.
           Otherwise: continue existing streaming text path unchanged.
       - In the message list render, if message.type === "pending_change":
           render <ConfirmationCard /> instead of a text bubble.
       - Add handleConfirm(pendingChange): POST to /api/operator-chat/confirm.
           On success: replace message with type:"confirm_success" bubble.
           On failure: replace message with type:"confirm_error" bubble.
           Do not remove the confirmation card on success — replace it with
           a success message showing what changed.
       - Add handleCancel(): replace message with type:"text", role:"assistant",
           text:"Got it — no changes were made."
  3C.3 End-to-end UX test in dev environment:
       Ask AI to set hours or add an FAQ. Confirm the flow:
       user message → pending_change card appears → click Confirm →
       success bubble appears → config updated in Supabase.
  Checkpoint: Full UX end-to-end works without page reload.

PHASE 3D: CONFIG STORE + UI STATE SYNC (1–2 days)
  3D.1 Create apps/dashboard/src/lib/config-store.ts
       Lightweight pub/sub module, same shape as mock-store.ts.
       Export:
         type ConfigStoreState = { version: number; lastUpdatedAt: string }
         subscribeToConfigStore(listener: () => void): () => void
         getConfigStoreState(): ConfigStoreState
         notifyConfigUpdated(): void
         useConfigStoreVersion(): number  (React hook using useSyncExternalStore)
       The version number increments every time notifyConfigUpdated() is called.
       Storage: in-memory only (not localStorage). Resets on page reload.
  3D.2 Update ConsoleSidebar handleConfirm():
       After a successful confirm POST, call:
         a. updateMockState() with the relevant field mutation (e.g., append
            FAQ to profile.faqs, update hours, update contacts).
         b. notifyConfigUpdated() to increment the config-store version.
       Per-tool mock store update helpers to add (in mock-store.ts or a
       separate apps/dashboard/src/lib/operator-tools/mock-store-updaters.ts):
         applyHoursChange(profile, toolArgs)
         applyFaqChange(profile, toolArgs, toolName)
         applyHandoffChange(profile, toolArgs, toolName)
         applyBehaviorChange(profile, toolArgs)
         applyBusinessInfoChange(profile, toolArgs)
  Checkpoint: After confirming a change, dashboard UI reflects new state
  without any page reload.

PHASE 3E: HARDENING (1–2 days)
  3E.1 Run npm run typecheck. Fix all TypeScript errors.
  3E.2 Run npm run lint. Fix all warnings.
  3E.3 Verify injection screening is applied to the operator-chat branch
       that calls generateText. The existing INJECTION_PATTERNS check from
       chat-handler.ts should be applied to the user message before it is
       passed to the LLM.
  3E.4 Verify no mock store fields are accidentally overwritten. Each
       applyXChange helper must do a targeted mutation, not a spread of
       the entire toolArgs onto the profile.

8. PHASE 6 — USAGE LIMITS AND TOKEN COST CONTROLS
====================================================
Dependency: Phase 3 complete (tool calling is the main LLM cost surface)
Note: Can start in parallel with Phase 5 once Phase 3 is done
Estimated effort: 3–5 days
Owner: 1 engineer

CONTEXT
--------
Token usage is currently untracked. maxTokens is hardcoded (400 for customer
chat, 800 for operator chat). There is no per-location budget, no usage
visibility, and no rate limiting. Phase 6 corrects this without exposing any
cost complexity to operators.

TASK LIST
----------

6.1 ADD TOKEN COUNTING TO LLM RESPONSES
  Modify packages/shared/src/llm/client.ts (or providers/openai.ts):
    - After each llmGenerate() or llmStream() call that has usage data in the
      OpenAI response (response.usage.total_tokens), record the usage.
    - Create a usage recording interface: recordTokenUsage(event: UsageEvent).
    - This function is no-op in non-server environments; it writes to
      usage_events table in server contexts.
  
  Type: UsageEvent = {
    businessId: string;
    locationId: string;
    userId: string;
    chatType: "customer" | "operator";
    model: string;
    inputTokens: number;
    outputTokens: number;
    toolCallsCount?: number;
    timestamp: string;
  }

6.2 DATABASE MIGRATION — USAGE EVENTS TABLE
  File: supabase/migrations/YYYYMMDDHHMMSS_usage_events.sql

  CREATE TABLE IF NOT EXISTS usage_events (
    id               UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    business_id      TEXT NOT NULL,
    location_id      UUID REFERENCES business_locations(id) ON DELETE SET NULL,
    user_id          UUID REFERENCES auth.users(id) ON DELETE SET NULL,
    chat_type        TEXT NOT NULL CHECK (chat_type IN ('customer', 'operator')),
    model            TEXT NOT NULL,
    input_tokens     INTEGER NOT NULL DEFAULT 0,
    output_tokens    INTEGER NOT NULL DEFAULT 0,
    tool_calls_count INTEGER NOT NULL DEFAULT 0,
    created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
  );

  CREATE INDEX IF NOT EXISTS idx_usage_events_business_created
    ON usage_events (business_id, created_at DESC);

  -- No RLS: usage_events is internal only. Not exposed to operator queries.
  -- Only accessible via server-side admin routes.

  Create via: npm run migration:new -- usage_events

6.3 WIRE USAGE RECORDING INTO CHAT ROUTES
  apps/dashboard/src/app/api/chat/route.ts
    - After llmStream() completes, record usage event (chat_type: "customer").
    - Streaming responses: the OpenAI streaming API returns usage in the final
      chunk. Extract from the stream before returning to client (or use the
      includeUsage: true option if the SDK supports it).
  apps/dashboard/src/app/api/operator-chat/route.ts
    - After generateText() returns, record usage event (chat_type: "operator").
    - generateText returns result.usage with promptTokens + completionTokens.
  apps/dashboard/src/app/api/operator-chat/confirm/route.ts
    - Record any LLM usage that occurs during confirm execution (tool executor
      does not call LLM, so this may be zero — but ensure the accounting is
      present for future tool types that may call LLM).

6.4 RATE LIMITING ON OPERATOR CHAT CONFIRM
  Context: /api/operator-chat/confirm writes to the database. Without rate
  limiting, a compromised session or automated script could make hundreds of
  writes per minute.
  
  Implementation:
    - Add a simple per-user rate limiter using a windowed counter.
    - Use an in-memory counter map keyed by userId (acceptable for single-
      server deployment; revisit with Redis for multi-server).
    - Limit: 30 confirmed writes per user per hour.
    - On limit exceeded: return HTTP 429 with body { error: "Too many changes.
      Please wait before making more updates." }
    - Log rate limit hits with userId (for monitoring).
  
  Note: This is a production hardening step. The limit is intentionally
  generous (30/hour) — human operators won't hit it. It exists to catch
  runaway automated writes.

15. WORKER / BACKGROUND PROCESS CONSIDERATIONS
=================================================

EXISTING WORKER: scripts/worker/website-import-worker.ts
  Status: Functional. Requires Phase 1 hardening before Phase 2 depends on it.
  
  Phase 1 changes to the worker:
    - Structured error code output (dns_fail, blocked, timeout, parse_error,
      llm_error) instead of generic Error.message strings.
    - Stale-job reaper: on each poll cycle, query for runs in "running" status
      with updated_at < NOW() - 5 minutes and reset them to "failed" with
      error_code="timeout".
    - Comprehensive try/catch ensuring no crash leaves a job in "running"
      with no further update.
    - Per-job structured logging: console.info for each claimed job and result.

  Worker deployment:
    - The worker is a long-running Node.js process that must be started
      separately from the Next.js app server.
    - RUNBOOK.md should document how to start the worker in production.
    - In the Replit environment, confirm the worker can run as a background
      process alongside the Next.js dev server.
    - The worker polls the Supabase database directly using the Supabase client.
      It does not call HTTP routes — this is correct and should not be changed.

  Worker and onboarding connection:
    - Phase 2 onboarding UI polls GET /api/website-import/latest every 2 seconds.
    - The worker polls the database every 5 seconds for queued jobs.
    - This means there is a potential 5-second delay from "scan my website" click
      to the worker claiming the job. This is acceptable.
    - If the worker is not running, the scan will sit in "queued" indefinitely.
      The onboarding UI should show a timeout message after 90 seconds of no
      progress and offer a fallback to Stage 4 (manual setup).
      This UI timeout is built in Phase 2 and is separate from the worker's
      own stale-job reaper (which handles recovery for the database state,
      not the UI state).

  Future consideration (NOT in scope for Tandem 3.0):
    - If Tandem scales to many simultaneous signups, the single-process worker
      may become a bottleneck. The existing architecture already has
      atomic job claiming (queued → running), so multiple worker instances
      could run without conflict. This is a post-3.0 scaling concern.

NO NEW WORKERS are introduced in Tandem 3.0. The operator AI tool execution
happens synchronously within the confirm route handler (it is fast — a
database GET + in-memory mutation + database PUT). No background queuing is
needed for tool execution.

18. RISK ANALYSIS
==================

RISK 1: AGENT WRITE-BACK SECURITY SURFACE (CRITICAL)
  Description: The AI operator tool system creates a new write path into
  the database. If authentication, authorization, or argument validation
  has gaps, an attacker could modify any operator's configuration.
  Likelihood: Medium (if implementation shortcuts are taken).
  Impact: Critical (unauthorized data modification).
  Mitigation:
    - The confirm route re-resolves scope from auth — never trusts client payload.
    - Zod validation applied to all toolArgs before execution.
    - Length limits on all string fields.
    - URL fields validated against javascript: and data: scheme injection.
    - All confirmed writes logged with userId.
    - Phase 8 security review specifically tests injection and IDOR scenarios.
  Residual risk: Low if mitigations are implemented as specified.

RISK 2: MOCK STORE / SUPABASE STATE DIVERGENCE (HIGH)
  Description: The dashboard currently reads from the localStorage mock store.
  If an AI tool write updates Supabase but the mock store update helper
  (applyFaqChange etc.) has a bug, the operator will see stale data after
  a confirmed change. This creates a confusing "it said it worked but
  nothing changed" UX.
  Likelihood: Medium (array mutation bugs are easy to introduce).
  Impact: High (poor operator experience, loss of trust in the AI).
  Mitigation:
    - Each mock store update helper must be individually tested (unit test
      or manual verification for each of the 9 tools).
    - After confirming any change in dev, visually verify the overview panel
      reflects the new value.
    - The config-store version bump is a second-line refresh (if mock store
      update misses something, the page re-fetches from /api/location-config).
  Residual risk: Medium without unit tests; Low with tests.

RISK 3: WEBSITE IMPORT WORKER NOT RUNNING (HIGH FOR ONBOARDING)
  Description: Phase 2 onboarding depends on the worker to process scans.
  If the worker is not running in production, every onboarding scan will
  sit in "queued" indefinitely and the operator will see no progress.
  Likelihood: Medium (process restarts, environment issues).
  Impact: High (onboarding flow cannot proceed, first impression destroyed).
  Mitigation:
    - Phase 2 builds a 90-second UI timeout that gracefully falls back to
      Stage 4 (manual setup) if no progress is detected.
    - Add worker health monitoring: a simple last_poll_at column on a worker
      health table, or a heartbeat log entry. Alert if no poll in 2 minutes.
    - Document worker startup in RUNBOOK.md.
  Residual risk: Medium (depends on operational monitoring quality).

RISK 4: LLM MODEL BEHAVIOR VARIABILITY (MEDIUM)
  Description: Tool calling behavior (when the LLM chooses to call a tool
  vs. respond with text) varies between model versions. With toolChoice:"auto",
  the LLM may call tools when a conversational response was expected, or
  fail to call tools when the operator asks for a change in casual language.
  Additionally, gpt-5.2 is the configured default — its function calling
  behavior should be verified before Phase 3 cutover.
  Likelihood: Medium.
  Impact: Medium (unexpected tool calls, or AI not responding to change requests).
  Mitigation:
    - Test the 9 tools with a variety of phrasings during Phase 3B.3.
    - The confirmation card prevents any surprise writes — even if the LLM
      calls a tool unexpectedly, the operator must click Confirm.
    - Tune the operator system prompt to explicitly note the available tools
      and when to use them (vs. when to just answer a question).
  Residual risk: Low (confirmation gate prevents harmful surprises).

RISK 5: ONBOARDING STATE MACHINE EDGE CASES (MEDIUM)
  Description: The 6-stage onboarding flow has many state transitions. Edge
  cases (browser refresh mid-scan, network error during apply, partial apply)
  may leave the operator in an unclear state.
  Likelihood: Medium.
  Impact: Medium (confused operator, incomplete setup).
  Mitigation:
    - The state machine (onboarding-state-machine.ts) must handle the
      "unknown stage" case gracefully — default to Stage 1 URL input.
    - On browser refresh, re-detect stage from server-side state:
        if import run exists and is "succeeded" → go to Stage 3
        if import run exists and is "running" → go to Stage 2 (resume polling)
        if import run does not exist → go to Stage 1
    - This detection uses GET /api/website-import/latest on onboarding mount.
    - All "Skip for now" paths lead somewhere reasonable.
  Residual risk: Low if stage recovery logic is implemented.

RISK 6: PAGE DELETION BREAKING EXISTING OPERATOR BOOKMARKS (LOW)
  Description: Operators who have bookmarked /settings, /knowledge, /intents,
  /menus, /handoff, /widget, or /integrations will land on a 404 if pages are
  deleted before redirects are added.
  Likelihood: Low (small operator base at this stage).
  Impact: Low (frustration, not data loss).
  Mitigation:
    - Phase 4B.4 adds all redirects before Phase 4C deletes any pages.
    - Verify redirects work in dev environment before deleting any page files.
  Residual risk: Very low.

RISK 7: SUPABASE CONCURRENT WRITE RACE (LOW)
  Description: If an operator rapidly confirms multiple AI tool changes, two
  concurrent confirm requests could race on the fetch→mutate→write pattern,
  with the second write overwriting the first.
  Likelihood: Low (human confirmation flow makes rapid consecutive confirms
  unlikely; the UI replaces the card on confirm so a second card cannot
  be confirmed while the first is in flight).
  Impact: Low (one change might be lost in an extremely unusual scenario).
  Mitigation:
    - The rate limiter (30/hour) prevents rapid automated confirms.
    - In Phase 8, document this as a known limitation and note that optimistic
      locking (etag-based or version field) is a post-3.0 improvement.
  Residual risk: Very low.

  Phase 3 modifies the operator-chat route and ConsoleSidebar. If a rollback
  is needed:
    1. Revert apps/dashboard/src/app/api/operator-chat/route.ts to previous
       version (remove generateText branch, restore pure streaming via
       handleChatPost).
    2. Revert ConsoleSidebar.tsx Message type extension and new rendering.
    3. The new files (tool-definitions.ts, tool-executor.ts, confirm/route.ts,
       config-store.ts, pending-change-renderer.tsx) can remain in place —
       they are not called by any other system.
    4. The mock store helpers (applyXChange functions) are additive and
       cause no regression if not called.
  Rollback restores exactly the Tandem 2.0 operator advisory chat behavior.
  Risk of rollback: Low (clear revert targets).

PHASE 4 ROLLBACK
  Pages are added before old pages are deleted. Redirects are added before
  page files are removed.
  If needed:
    1. Revert next.config.ts redirects (remove the 7 redirect entries).
    2. Restore any deleted page files from git history.
    3. Revert ConsoleSidebar navigation to full list.
    4. Revert overview/page.tsx to prior version.
  The /chatbot page and panel components can remain (they do not affect
  other pages if navigation items pointing to them are removed).
  Risk: Low if each sub-phase has a clear commit boundary.

PHASE 5 ROLLBACK
  Operator chat history: revert the GET/POST /api/operator-chat/history routes.
    If ConsoleSidebar reverts its history-loading mount logic, the table
    remains in Supabase but is no longer written to. No data corruption.
  Onboarding Stage 4 tool-calling: revert to form-based fallback (Phase 2 code).
  Risk: Low.

PHASE 6 ROLLBACK
  Usage recording is fire-and-forget (errors are logged but do not fail
  requests). If the usage recording has a bug, it can be disabled by reverting
  the recordTokenUsage calls without affecting chat functionality.
  The usage_events table remains but stops receiving new rows.
  Rate limiter: revert the 429 check in the confirm route. No data impact.
  Risk: Very low.

GIT STRATEGY FOR ROLLBACK
  Each phase should have a clearly labeled commit (or PR) so that git revert
  targets are unambiguous. Recommended commit messages:
    "feat(phase-1): stabilize import pipeline with error codes and stale-job reaper"
    "feat(phase-2): new AI-guided onboarding flow"
    "feat(phase-3a): operator AI tool definitions and LLM integration"
    "feat(phase-3b): confirm endpoint and tool executor"
    "feat(phase-3c): confirmation card UI in ConsoleSidebar"
    "feat(phase-3d): config-store for UI state sync after AI writes"
    "feat(phase-4a): overview page redesign with state panels"
    "feat(phase-4b): navigation restructure (4 sections, chatbot page)"
    "feat(phase-4c): page cleanup, conversations improvement"
    "feat(phase-5): AI tool calling integration, session persistence"
    "feat(phase-6): usage tracking and rate limiting"
